### 5. 最终Source Integrity检查失败 (致命错误)

**日志证据**:
```
❌ [Live Charting Program 1_chunked - 副本.srt] 失败：final lint source integrity failed: 语义翻译回流后的原始 cue 顺序或文本发生变化；已阻止将该结果视为高质量完成。
```

**根本原因**:
- 原始字幕 2194 条，重组后 1874 条（合并了320条）
- `finalize_entries()` 会进一步合并相邻重复条目
- 合并操作导致 source_cue 签名（index, time, text, source_indexes）发生变化
- 严格检查认为这是"数据损坏"，阻断流程

**技术细节**:
```python
# pipeline.py line 683-697
final_integrity_errors = source_integrity_errors(original_cues, final_entries, ...)
if final_integrity_errors:
    raise RuntimeError("final lint source integrity failed: ...")
```

**为什么这是误报**:
- 合并操作是**有意为之**的优化，不是数据损坏
- source_cues 中保存了原始来源信息（source_indexes）
- 只是签名格式变了，实际内容完整

**建议方案**:
1. **降级为警告**（推荐）- 标记needs_review，不阻断
2. **跳过检查** - 对已标记needs_review的条目不做严格检查
3. **修改签名逻辑** - 不比较source_indexes，只比较source_text

## 根因总结

```
翻译API返回原文(无需翻译的内容)
    ↓
译文硬检查: 译文不含中文 → 判定为"漏译"
    ↓
漏译修复: 重新翻译 → API再次返回原文 → 修复失败
    ↓
忠实度审校: 这2条始终是原文 → 标记needs_review
    ↓
source_integrity检查: 合并导致签名变化 → 致命错误
    ↓
整个流程失败，无输出
```

**核心问题**:
1. **译文硬检查过于简单** - 只看是否含中文，不区分"漏译"和"无需翻译"
2. **source_integrity检查过于严格** - 不允许合理的合并操作

## 修复建议

### 优先级 P0 (必须修复)

1. **放宽source_integrity检查**
   - 将致命错误改为警告
   - 或者在finalize_entries后重新计算基准签名
   - 位置: `core/pipeline.py:683-697`

### 优先级 P1 (应该修复)

2. **改进漏译修复逻辑** - 需要区分"真正漏译"和"无需翻译"
   - 当前逻辑: 译文不含中文 → 判定为漏译 → 重新翻译
   - 问题: 对于"无需翻译的内容"（口头禅、数字），API会返回原文，被反复判定为漏译
   - 位置: 需要查找漏译修复的相关代码

3. **翻译失败的根本原因** - ✅ 已定位

   **ID 1697**: `Lulu, lulu, lulu, lulu, lulu.`
   - 这是主播的口头禅/模拟交易时的噪音
   - 翻译API正确返回原文（无需翻译）
   - 被"译文硬检查"误判为漏译

   **ID 1724**: `1, 2, 3.`
   - 这是数数字
   - 翻译API正确返回原文（无需翻译）
   - 被"译文硬检查"误判为漏译

   **结论**: 不是真正的翻译失败，是检查逻辑的误报

   **修复方案**:
   - 在"译文硬检查"中增加白名单/豁免规则
   - 对于以下情况不判定为漏译:
     - 纯数字/数数字 (1, 2, 3)
     - 口头禅/拟声词 (lulu, hmm, okay, yeah)
     - 专有名词 (NASDAQ, S&P 500)
     - 短于3个单词的无实义内容

### 优先级 P2 (可以改进)

4. **批量处理容错**
   - 即使有少量条目失败，也应该导出结果
   - 标记needs_review但不阻断整个流程
