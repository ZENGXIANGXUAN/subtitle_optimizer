# 并发与流程审计（2026-07-22）

## 症状

界面允许设置 1–100 并发；用户设置 70 后，单文件字幕处理仍然缓慢。

## 根因

`SubtitlePipeline` 在初始化时将用户值静默限制为最多 8：

```python
self.concurrency = max(1, min(self.QUALITY_MAX_CONCURRENCY, int(concurrency)))
# QUALITY_MAX_CONCURRENCY = 8
```

批大小同样被静默限制为最多 8。界面仍显示“并发数 (1–100)”和“批大小
(1–50)”，构成配置语义与实际执行不一致。

此外，`BatchWorker._run` 使用 `for filepath in self.files` 顺序处理文件；该
并发值不用于同时处理多个字幕文件。

## 证据

- 2026-07-21 19:13–19:33 的日志中，按 API 请求发送/成功响应配对计算，峰值
  在途请求正好为 8。
- 同一窗口内共发送约 1,218 个 API 请求：翻译、忠实度、优化和全文一致性是
  依次执行的完整阶段，不能彼此并行。
- 代码位置：`core/pipeline.py` 的 `QUALITY_MAX_CONCURRENCY = 8` 和初始化
  限制；`ui/main_window.py` 的 1–100 输入；`core/workers.py` 的顺序文件循环。

## 流程审计结论

正确性方向合理：分阶段快照、自动重试、保留原文兜底可避免字幕丢失。

性能设计存在三项问题：

1. 隐藏的 8 并发上限违背用户配置；
2. 所有字幕都经过多轮 LLM 审校，导致请求数随 cue 数线性放大；
3. 已进入 `source_fallback` 的条目在调用审校 API 后才被跳过，仍消耗请求。

## 建议

不要直接把 70 无条件放开。应把“用户请求并发”“翻译并发”“质量阶段并发”
分开显示，并在本地代理上用 8、16、32 的实测吞吐和错误率选择默认值；同时让
界面显示实际生效值。对多文件任务，应另设文件级并发。

## 8 并发上调评估

- 应用层并发安全：各阶段在请求前冻结字幕快照；并发任务只写各自的条目位置，
  计数器有锁，HTTP 连接池也按生效并发扩大。因此 8 → 16 不会造成数据竞争。
- 运行证据：本次任务主处理窗口的峰值为 8，平均在途约 6.1（约 76% 的 8 槽
  利用率）；没有真实 429、5xx 或网络超时。历史 JSON/漏 ID 问题来自输出协议，
  而不是并发拥塞。
- 局部上限：一致性指南构建固定最多 4 并发，逐条漏译修复也固定最多 4；提高
  主并发不会加速这两段。
- 风险：本地代理的上游容量未知，70 可能只把排队转移到代理端；本地代理模式
  的客户端传输重试为 1 次，突发拥塞时恢复能力较弱。

已实施第一档：主流程最大并发改为 16，界面标签、输入校验、单文件/批量参数
归一化和历史配置加载全部使用同一上限。历史配置中的 70 会显示并生效为 16。
一致性指南与单条漏译修复仍保持 4 并发。

后续可测试 32；若吞吐增长不足 25% 或出现 429/5xx/超时/JSON 错误率上升，则
回退。70 应作为明确的压力测试值，而非默认生产值。

验证：`python -m pytest -q` 通过，76 passed，3 subtests passed。
