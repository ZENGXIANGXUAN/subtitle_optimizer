# 字幕翻译与质量门禁故障复盘

## 事实证据（2026-07-21 19:13–19:16）

- 应用日志记录了 315 次 HTTP 200；网络/超时错误和非 200 响应均为 0。
- 使用本地代理 `127.0.0.1:8000` 时，客户端传输层记录为 `尝试 1/1`；
  该模式刻意关闭了嵌套网络重试。翻译业务层仍对不合格条目进行一次
  覆盖补齐重试，发生 18 次。
- 最终被标为翻译失败的 5 条（411、1369、1553、1723、1750）均在随后的
  自动修复请求中收到非空结果；例如 411 返回“5月初市场出现大幅下跌”。

## 根因

翻译失败不是网络故障，也不是模型没有作答。`_translation_looks_incomplete`
将英文词数和中文字符数作硬比例比较：18 个及以上英文词必须至少有 12 个
汉字。上述 5 条有效、简洁的字幕分别只有 10、11、11、0、0 个汉字，于是被
程序丢弃、回退为英文原文，并在忠实度、优化和一致性阶段反复触发同一错误。

这是把长度启发式误当作语义审核的逻辑冲突。日志中忠实度审校 11 次失败有 8
次、优化 2 次失败全部、术语一致性 5 次失败有 4 次均由此触发。

另有独立的模型输出协议问题：审校提示词要求未被代码使用的 `reason` 字段，
导致少量 JSON 尾随解释、缺失数组括号或漏 ID；这不是网络错误。

## 修复

- 翻译可用性硬校验现在只拒绝空译文或实质英文原文的英文泄漏；不再根据中英文
  字符比例否决已经含中文的字幕。
- 数字计数和重复语气词等非语义 cue 自动放行，不再强行要求汉字。
- 忠实度/一致性请求仅要求 `id` 与 `tgt`；JSON 解析器会保留第一个完整 JSON
  值，忽略其后模型擅自附加的解释，并修复仅缺最终容器符号的响应。
- 未保留“待人工复核也导出”的路径。有效译文自动继续；真正没有可用译文时，
  自动保留原始 cue 为单行字幕并继续导出，标记为非阻断的 `source_fallback`，
  后续审校与双语质检跳过该 cue，避免字幕丢失或质量门禁与兜底逻辑冲突。
